## 1. PHYSICAL DATABASE ARCHITECTURE & STORAGE ENGINE

### 1.1 Purpose of the Physical Database Specification
The **Physical Database Design & Implementation Specification** defines the low-level relational schema, column data types, primary and foreign key constraints, 3NF normalization proofs, performance indexes, and transactional boundaries for **KV-TMS**.

While the conceptual ER diagram defines high-level business entities, this physical specification serves as the blueprint for **database administrators, ORM mapping layers, and production SQL deployments**.

### 1.2 Enterprise Relational Technology Stack
* **Production RDBMS:** PostgreSQL 16 Enterprise Relational Database with ACID transaction guarantees.
* **Test & Development Engine:** H2 In-Memory Relational Database (PostgreSQL compatibility mode).
* **Persistence / ORM Framework:** Spring Boot 3.x with Spring Data JPA and Hibernate 6.x.
* **Connection Pooling:** HikariCP connection pool configured for high-concurrency retail POS traffic.
* **Physical DDL Source:** `04 Database/SQL/schema.sql` (fully executable migration script).

### 1.3 Physical Naming Conventions & Storage Standards
* **Table Identifiers:** Plural, snake_case strings (e.g. `course_trades`, `attendance_records`, `sales_orders`).
* **Primary Keys:** `BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` for scalable 64-bit auto-incrementing surrogate keys.
* **Monetary Quantities:** Precise `DECIMAL(10,2)` data types to eliminate floating-point rounding errors in retail POS sales and DBT piece stipends.
* **Temporal Auditing:** Standardized `TIMESTAMP DEFAULT CURRENT_TIMESTAMP` for transaction provenance.

## 2. FORMAL NORMALIZATION ANALYSIS (1NF, 2NF, 3NF PROOF)

To eliminate data redundancy, enforce data integrity, and prevent insertion, update, and deletion anomalies, the KV-TMS physical schema strictly adheres to **Third Normal Form (3NF)**:

### 2.1 First Normal Form (1NF) Compliance
**Criterion:** A table is in 1NF if and only if all attribute domains contain only atomic (indivisible) scalar values, and each record is uniquely identifiable by a primary key.
* **Atomicity:** All composite and multi-valued fields are decomposed into discrete columns (e.g., student name, contact info, and trade enrollment are stored as separate atomic primitives; no comma-separated arrays).
* **Primary Key Mandate:** Every table incorporates an explicit, non-null primary key (`user_id`, `trade_id`, `attendance_id`).

### 2.2 Second Normal Form (2NF) Compliance
**Criterion:** A table is in 2NF if it is in 1NF and every non-prime attribute is fully functionally dependent on the primary key (no partial functional dependency on composite keys).
* **Elimination of Partial Dependencies:** In associative junction tables such as `attendance` (linking `trainee_id` and `training_id`) and `product_creations` (linking `trainee_id` and `product_id`), surrogate identity primary keys (`attendance_id`, `creation_id`) are utilized. Attributes such as `status` or `units_crafted` depend upon the entire transaction event, satisfying full functional dependency.

### 2.3 Third Normal Form (3NF) Compliance
**Criterion:** A table is in 3NF if it is in 2NF and no non-prime attribute is transitively dependent on the primary key ($X \rightarrow Y \rightarrow Z$ is eliminated).
* **Elimination of Transitive Dependencies:** 
  * In the `trainees` table, trade details (e.g., `trade_name`, `duration`) are not stored directly; instead, only the foreign key `trade_id` is maintained. Trade attributes reside exclusively in `course_trades`.
  * In the `trainings` table, faculty domain credentials reside exclusively in `trainers` via `trainer_id` FK, preventing instructor data duplication across dozens of workshop sessions.

## 4. PERFORMANCE INDEXES, CONCURRENCY & VERIFICATION

### 4.1 Indexing & Query Optimization Strategy
* `idx_users_username:` Unique B-Tree index on `users(username)` for instantaneous authentication lookups.
* `idx_attendance_lookup:` Composite index on `attendance(trainee_id, attendance_date)` to rapidly compute 75% statutory attendance percentages.
* `idx_sales_product_date:` Composite index on `sales_orders(product_id, sales_date)` optimizing the 90-day time-series window for Holt-Winters AI demand forecasting.
* `idx_inventory_product_type:` Composite index on `inventory(product_id, item_type)` supporting atomic two-tier warehouse balances.

### 4.2 Concurrency Control & Transaction Isolation
* **Pessimistic Row Locking:** Retail POS checkout transactions acquire `SELECT ... FOR UPDATE` on `inventory` rows to prevent race conditions and inventory overselling during simultaneous retail transactions.
* **ACID Isolation Level:** Database operates under PostgreSQL default `READ COMMITTED` isolation level with atomic rollback on runtime validation failures.

### 4.3 Referential Integrity & Cascade Action Policy
| Foreign Key Relationship | ON DELETE Action | Integrity Justification |
| :--- | :--- | :--- |
| `trainers.user_id &rarr; users.user_id` | `CASCADE` | Deleting user account removes associated faculty profile. |
| `trainees.trade_id &rarr; course_trades.trade_id` | `SET NULL` | Preserves student enrollment history even if trade track retires. |
| `inventory.product_id &rarr; products.product_id` | `RESTRICT` | Prevents accidental catalog deletion while active stock exists. |
